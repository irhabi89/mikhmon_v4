# Sales sync (SQLite ↔ MikroTik)

**MIKHMON v4 — GHAIB-NETWORK Edition**  
Maintained by PT GHAIB-NETWORK · Developer: quiqxiq.

## One-time upgrade

```bash
composer install --no-dev --optimize-autoloader
bin/mikhmon db:migrate --backup
bin/mikhmon db:maintenance --check
bin/mikhmon sync:run --session=<router>
```

The baseline migration parks the old sales tables as
`sales_records_legacy_v1` / `sales_import_queue_legacy_v1` and creates:

- `sales_records` — report table (normalised date/month/price, pagination indexes).
- `sales_router_records` — complete snapshot of `/system/script` sales records;
  `state` is the import queue (`pending|imported|invalid|deleted`).
- `sales_sync_runs` — progress, heartbeat, reconciliation counts.

The router scan is the source of truth. A full scan must complete before the UI
shows `in_sync=true`.

## Commands

```bash
bin/mikhmon sync:run --session=<router>            # full scan + import + verify
bin/mikhmon sync:run --session=<router> --month=nov2026
bin/mikhmon sync:status --session=<router>         # JSON, no router connection
bin/mikhmon sync:worker --run-id=<id>              # background worker
bin/mikhmon db:maintenance --backup --vacuum --optimize --check
bin/mikhmon db:import-legacy --from=data/mikhmon.db.backup
bin/mikhmon db:clear-sales --session=<router> --yes   # local DB only, router untouched
```

## Reconciliation rules

- `matched` / `missing` / `extra` are set comparisons by script `name`.
- `coverage = matched / router records`.
- `exact = matched / (matched + missing + extra + invalid)`.
- `in_sync` is true only when a full scan is complete and
  `missing=0, extra=0, invalid=0`.
- A DB with the same number of rows but different names is **not** 100%.

## Performance notes

- Router scans use one streamed API response (`!re` per row, bounded memory).
- `sales_records` has `(session, date_key, time_key, id)` and month/username indexes.
- The report page never opens a router connection; only the sync worker does.
- `MIKHMON_SYNC_WORKER=web` can force the chunked month fallback when the host
  disables `exec`.


## Hotspot server tracking

New sales records append `|#MMSRV1#|<hotspot-server>` to the script name.
`RecordParser` strips it into `sales_records.server_name`.

Profiles generated by Mikhmon get a server lookup on save. To upgrade
existing profiles safely:

```bash
bin/mikhmon router:onlogin-upgrade --session=<router>          # dry run
bin/mikhmon router:onlogin-upgrade --session=<router> --apply  # backup + apply
bin/mikhmon router:onlogin-rollback --session=<router> --file=data/backups/onlogin-....json
```

Old records have `server_name=''` and can be filtered with
`server=__none__`. Reports/export/print and the dashboard server cards support
the `server` filter.

## Live fallback when the database is empty

`process/live_sales.php` streams sales records directly from
`/system/script/print` as NDJSON. It is read-only: it does not write SQLite and
does not start a sync/background job. The report page shows a “Data langsung
dari MikroTik” banner and appends rows as they arrive.

## Accurate unsynced percentage

For a completed scan:

```text
unsynced = missing (snapshot rows not present in sales_records)
unsynced_percent = unsynced / router_total * 100
synced_percent = matched / router_total * 100
archive_extra = db_total - matched
```

If the scan is incomplete, percentages are `null` and the UI says
“Belum diverifikasi”. `archive_extra` is shown separately and is not counted as
unsynced.

## Manual import: delete MikroTik sales records

The sync modal has an opt-in checkbox. After a successful manual import and
verification, only snapshot rows in state `imported` are deleted from
`/system/script`. Each name is revalidated with `RecordParser::isSalesRecord`;
non-sales scripts are never deleted. Invalid/pending records are left in place.

## On-login webhook fallback

Per-session settings can hold a webhook URL and token. On-login v3 tries
`/tool fetch` to `process/sales_webhook.php`; regardless of webhook success, the
script record is always written to `/system/script`. This guarantees a
durable fallback if the webhook is unreachable or returns an error. The webhook
is idempotent because `sales_records` has `UNIQUE(session, name)`.

Existing profiles must be re-saved (or upgraded) to receive the new webhook
snippet; profiles without webhook still write the durable script record.
